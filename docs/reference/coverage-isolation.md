# 覆盖率分片的计算隔离

SYS-C2E2F的实际CI44452217543中，两份覆盖率进程在同一runner并行。
全部4259用例无断言错误，合并行覆盖率93.1%，但核心分片122.779秒超过
原120秒门限，前端分片112.192秒。该次CI失败保留，不能用覆盖率或本地通过覆盖它。
原JUnit中，核心RRC边界/存储合计22.967秒，前端stream_rrc_word为78.660秒；
这些是当次共享runner上的观测，不是算法硬件成本或独立运行时间。

## 作业与合并规则

核心/前端分片分别使用独立的`ubuntu-latest` runner；
没有减少用例、提高超时、重试失败测试或改变接收算法。
每片实际安装并检查纯Python后端，记录20项最长测试耗时，并始终上传：

- 分片命名的后端元数据，避免合并时同名覆盖。
- 原始coverage数据库、JUnit及完整pytest日志。

`Python Coverage`等待两片结束，下载本次运行的两份制品并组合真实覆盖率。
`check_test_shards.py`继续要求各片小于120秒、零错误/失败且无重复用例；
合并行覆盖率门限继续为90.1%。片失败、缺数据库/JUnit或合并失败均不能计通过。
聚合作业即使在某片失败后也保留可获得的诊断；取消时不伪造剩余结果。

独立runner增加CI并发资源，不能计为接收算法计算、FPGA吞吐或资源改善。
新提交需核验实际作业、每片时长、后端和官方制品；不能预设隔离一定满足时长门。
原始失败制品、提交及输入关联位于冻结根的`timing-service-handoff`，
与[实际有限定时服务](timing-service-handoff.md)证据一起保存。

## 单元测试隔离及制品链

上述重分片提交4cb7108的实际CI44479380726仍失败：纯Python核心103.165秒，
前端131.690秒超原120秒门，4291用例零断言失败。前端当次JUnit中
`stream_rrc_word`为76.728秒，另外五模块合计约54.962秒。
不能从覆盖率耗时直接推断普通并行测试的耗时，也不能仅凭这两次观测证明竞争原因。
该次Python/Rust算法检查结果、原始JUnit和六份官方制品继续保留。
依赖的覆盖率分片未运行，聚合缺报告失败；没有伪造覆盖率结果。

保留两片/后端及当前全部用例，将四个单元测试矩阵项分别放在独立runner。
每片保存实际后端、原始JUnit、完整日志、独立120秒预算判定及片内诊断；
失败或报告缺失时作业失败，并尽可能上传已生成的证据。片内诊断分别放在
`receiver-diagnostics/unit-core`与`unit-front`，避免合并覆盖。

原接收验证作业等待单元分片后下载本次同后端的两份制品，核对提交和实际加速后端，
再次检查JUnit时长、零断言失败及用例互斥，再执行原算法审计。
每种后端的单元原始制品仍单独保留，汇总制品也包含相同字节的报告、预算和诊断。
即使单元阶段失败，仍尝试执行独立算法审计并保存结果；不会把部分通过计为CI整体通过。

完整正常运行现在预期15项实际作业、12份官方制品；任务失败或取消时数量可能不足，
必须报告实际数量及未运行项，不填充成功记录。独立覆盖率仍是两片及90.1%门。
增加的是CI并发资源，不能算入算法运算、FPGA资源共享或16MS/s能力。
是否满足120秒仍须由新CI证明，不保证所有后续runner的运行时间。
