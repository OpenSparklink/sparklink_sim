# 捕获细搜的可选回调兼容性

M26 的实际 CI `45101475554` 中，两个后端的主验证失败。
实际捕获到头 CRC/合法帧尾的新增步骤通过，首个失败发生在既有功率复用诊断：
`CaptureFineWorker` 在未启用选择缓存时仍传 `sink=None`，而 `ObservedFlow.run()`
已经安装自己的诊断 sink，Python 因重复关键字抛出 `TypeError`。
下游模型缺少 `model.json` 是这次异常的后果，不能归成接收数值或资源失败。

这是模型调用约定的兼容性修复，仍实现既有 §6.2.3 同步处理，
不引入空口特性；标准版本与原件 SHA 见[标准来源](standard-sources.md)。

## 调用约定

- `capture_selection=False`：保持原引擎调用，只传源字、模板、峰和原几何参数。
  诊断包装器继续拥有自己的 sink，不接收新增的空回调关键字。
- `capture_selection=True`：按实际选中缓存协议传入一次非空回调，保留有序样本、
  单信用、真实可用沿和取走/取消行为。
- worker 的 `(event,result)` 诊断回调与底层逐事件 sink 是不同接口。
  异常继续传播，未实现观察器不能返回成功或交付帧。

修复仅使可选关键字在编译功能启用时出现；没有额外 DSP、RAM、端口或寄存状态。
原完整增长、归一化排序、峰值等待、所有权和数值/资源门继续独立检验。

## 复现和证据

两后端的实际失败主制品均按官方 SHA/ZIP CRC 保存；从原 CI 制品提取了 443 个
捕获父输入成员，逐项记录原 SHA，没有重新生成或替换 IQ。
原提交上重放得到相同 `TypeError`；新增反例在修复前为 6 失败/2 通过。
反例覆盖 FT2/3/4 的实际 `ObservedFlow` 及旧签名包装器、显式缓存回调、异常传播。

修复后原 30 个搜索窗的全部候选分数、采样、原默认微轨迹保持冻结参考；
原基线/功率复用周期合计仍为 4180197/3872765。
模型命令仍返回预期的 1，表达原完整接收/资源门尚未关闭，不把诊断恢复计为射频收益。

标准 `PYTHONPATH=src` 测试入口下新增 8 项反例，原用例身份全部保留。
纯 Python / 真实 Rust 加速环境全量分别为 5603 / 5614 项，覆盖率 93.87% / 93.86%，
七分片最大耗时 65.569 / 62.183 秒；依赖跳过分别为 38 / 5 项。
测试脚本的首次全量收集曾因诊断脚本相对导入失败，原报告保留；
现在仅在实际包装器测试内安装脚本路径，不改变项目 CI 的导入环境。

设 `RX_EVIDENCE_ROOT` 为本任务冻结证据根，在该修复源码目录可运行：

```sh
PYTHONPATH=.:src:scripts python scripts/model_spline_power.py \
  --capture-root "$RX_EVIDENCE_ROOT/capture-sink-compatibility/frozen-CI-capture" \
  --output /tmp/power-sink-recheck
```

输出目录应不存在；依赖使用本提交 `uv.lock`。全部输入 SHA、基线失败、修复后结果、
单元/覆盖率、原源码差异及实际 CI 状态见 `capture-sink-compatibility/`。
旧失败运行不回写为通过，修复提交需要自己的实际 CI。
其它下游生产者也要实际复核，不能由这一条命令推断整链 16 MS/s 或 FPGA 能力。
